## Before fresh benchmark inference

The 48-run Qwen9 audit found 56 format errors and exactly 56 truncated responses; every rejected turn was length-limited. All 56 raw responses opened a command fence and none closed it. Eight missing submissions occurred with zero executed actions. Thus interface delivery and output budget deserve early priority; a formatting reprimand alone cannot establish an algorithmic failure. Failed attempts consumed 288,284/299,459 output tokens (96.3%). There were also six runs passing examples but failing official tests and only one recovery to official success, so interface repair alone is unlikely to solve the reasoning problem.

A real LiteLLM HTTP-handler mock confirmed that 1.81.16 drops assistant tool calls and tool result names from native history. The versioned `extra_body.messages` override preserves both, reasoning fields and sampling options. No installed package changed. Three transport tests pass. On existing negative/functional synthetic tasks, stock→fixed required 9→5 and 15→8 actions, 679→297 and 910→450 output tokens; all passed public tests. This establishes a mechanism, not benchmark accuracy.

Allocation-only probes at 32K/64K/128K used 6.718/7.683/9.897 GB, respectively, all fully on GPU. Total GPU memory at 128K was 13,262 MiB including desktop/background usage. These short requests do not establish full-length prefill performance or prove the task needs 128K.

## Presence and thinking sampler results

Nonthinking presence=0 vs 1.5: 1/3 vs 2/3 correct, 207.5 vs 176.0 seconds, 17,362 vs 14,189 generated tokens. The gained easy-task success is candidate correctness (both arms execute commands), not simply a repaired command fence. Both hard attempts hit three 4K caps with no candidate; presence=1.5 reduces repeated 12-word sequences (maximum 5/2/2 across its three responses vs 10/12/4 for presence=0) without completing delivery. Retain presence=1.5 for broader configuration selection, but do not infer general significance from three problems.

On the previously examined medium, native 128K/32K thinking with T=.2/presence=1.5 delivers a candidate in 109.6 seconds/9,601 tokens without format errors, passes public tests and fails official judging. The coding preset (T=.6/top_p=.95/top_k=20/presence=0) reaches the wall after 602.1 seconds, with 43,210 observed output tokens plus an unobserved final call; its preserved candidate also fails. Eliminate both as default candidates on this evidence. The general vendor thinking preset (T=1/top_p=.95/top_k=20/presence=1.5) remains a justified, distinct candidate; compare text/native on one medium before spending more.

Next `dev-nonthinking-large-output`: one previously truncated hard task, text/nonthinking/T=.2/presence=1.5, 64K context/32K output/480-second query, same 600-second wall. This is an explicit combined larger-context/output candidate, not a claim that context alone causes improvement. Compare its raw initial prefix against the 16K/4K trace to see whether larger context changed the early generation. It tests a less repetitive truncated program, whereas the earlier 32K thinking failure was a long internal reasoning loop. Stop this candidate if it only prolongs failure.

Termination audit: none of the 29 original runs with a passing public test changes source after its *first* passing test; only 30 total subsequent actions remain, mostly explicit submission. This supports a potential small counterfactual saving, not a measured new policy. Do not introduce automatic public-pass submission/checkpointing yet. Compound checker commands such as pipes remain outside the defined recognized-check repair accounting; their shell return code can mask failure. They remain visible manual actions within the shared action/wall caps, and are not mislabeled as trusted passing checks. No claim is made that three recognized-check repair groups caps every conceivable manual revision.

## Final development screens and selection shortlist

The nonthinking 64K/32K combined budget reaches 600 seconds with no submission; its captured first response uses 32,768 tokens, leaves a fence open and repeats a 12-word sequence 34 times. Its prefix differs from the 16K/4K run, so the separate contribution of context is not identified. Stop this candidate. General-vendor thinking also fails the medium with native/text protocols at 602.1/525.9 seconds and 48,922/45,752 captured tokens. Stop their two unstarted hard jobs; do not run more of these unmodified slow configurations.

A further concrete sampler hypothesis follows from [Ollama's repetition-window documentation](https://docs.ollama.com/modelfile) and [llama.cpp's shared penalty-sampler wiring](https://github.com/ggml-org/llama.cpp/blob/master/common/sampling.cpp): repeat_last_n=64 can miss longer-range reasoning loops. In the first low-temperature 32K thinking trace, the ten most frequent 12-word sequences recur at median gaps of 145 words, often well beyond 64 tokens. This is a hypothesis about the installed backend, not a claim of exact equivalence to Hugging Face presence penalties.

Controlled nonthinking window 64→1024 on the previously truncated hard task produces a complete candidate without format errors in 51.3 seconds/3,985 tokens vs 134.4 seconds/12,288 tokens and missing submission. The candidate passes examples but fails official judging. Backend logs explicitly confirm repeat_last_n=1024. Given this delivery/efficiency signal, test the same single window change in general native thinking on the medium: first response falls from 30,239 to 9,279 tokens; the run officially passes in 305.7 seconds/26,233 tokens, where window64 had failed at 602.1 seconds. This is still far costlier than the 29-second successful nonthinking control, so it is a high-reasoning candidate, not the default by assumption.

Freeze the fresh selection shortlist: original control; presence-only 1.5 text; explicit prior tag sampler (T=.2/top_p=.95/top_k=20/presence=1.5) text; presence1.5/window1024 text; and general native thinking/window1024/128K/32K. Run all 12 selection tasks with seed2108, 60 planned attempts, with an initial checkpoint after 15 attempts (one task per difficulty, all five arms). Interleave difficulty and rotate profile order. Stop clearly inefficient/unreliable arms when supported; execution filters leave their frozen jobs explicitly unstarted rather than altering profiles/results. A second seed2109 comparison of the leading practical configuration against control is planned, with another contender repeated if ambiguous. No held-out outcomes inform this selection.

Expected remaining inference is a few hours based on the measured short-budget attempts, within the original 10-hour/3M-token ceiling.
